1 — Security im Entwicklungsprozess

Sicherheit entsteht nicht durch einen einzelnen Test vor dem Release, sondern in jeder Phase (Secure Software Development Lifecycle, „Shift Left“ – Fehler möglichst früh finden):

PhaseSecurity-Aktivität
AnforderungenSchutzbedarf der Daten klären, Rollen und Berechtigungen festlegen, Sicherheitsanforderungen aus dem ASVS auswählen
EntwurfThreat Modeling: Was kann schiefgehen? Wo sind Vertrauensgrenzen? (Lektion 1.1)
Implementierungbewährte Bibliotheken, OWASP Cheat Sheets, Code-Reviews mit Security-Blick
Testautomatisierte Security-Tests in der CI-Pipeline, Abhängigkeiten prüfen, ggf. Penetrationstest
BetriebSecurity Logging und Monitoring, Updates einspielen, auf Vorfälle reagieren
ℹ
Threat Modeling mit STRIDE

Ein einfacher Einstieg ist, für jede Komponente sechs Fragen zu stellen: Kann jemand eine fremde Identität vortäuschen (Spoofing)? Daten manipulieren (Tampering)? Eine Aktion abstreiten (Repudiation)? Daten einsehen (Information Disclosure)? Das System lahmlegen (Denial of Service)? Mehr Rechte erlangen (Elevation of Privilege)?

2 — Secrets Management und Environment Variables

Secrets sind alle Geheimnisse, die eine Anwendung zum Betrieb braucht: Datenbank-Passwörter, API Keys, JWT-Signaturschlüssel, OAuth-Client-Secrets, der Pepper aus Lektion 1.2. Gelangen sie in falsche Hände, sind alle anderen Schutzmaßnahmen umgangen.

Konfiguration vom Code trennen

Secrets gehören nie in den Quellcode und nie ins Git-Repository – auch nicht in ein privates, denn Repositories werden geteilt, geforkt und kopiert, und die Git-Historie vergisst nichts. Stattdessen liest die Anwendung Konfiguration aus Environment Variables (Umgebungsvariablen), die je nach Umgebung (Entwicklung, Test, Produktion) unterschiedlich gesetzt werden.

  • Lokal stehen die Werte oft in einer .env-Datei – diese wird in .gitignore eingetragen. Ins Repository kommt nur eine .env.example mit Platzhaltern.
  • In Produktion verwaltet ein Secrets Manager die Werte (z. B. HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, die Secret-Verwaltung von GitHub Actions oder Kubernetes): zentral, verschlüsselt, mit Zugriffsrechten und Protokoll.
  • Secrets regelmäßig und nach jedem Personalwechsel rotieren; pro Umgebung verschiedene Secrets.
  • Secret Scanning (z. B. Push Protection von GitHub) erkennt versehentlich eingecheckte Schlüssel.
✗
Secret geleakt – was tun?

Ein Secret, das einmal in einem Repository, Chat oder Log stand, gilt als kompromittiert. Es zu löschen reicht nicht. Sofort widerrufen und durch ein neues ersetzen, danach prüfen, ob es missbraucht wurde.

3 — Dependency Security und Supply Chain

Eine typische Web-Anwendung besteht zum größten Teil aus fremdem Code: Ein neues Frontend-Projekt bringt schnell hunderte npm-Pakete mit. Jede Abhängigkeit kann Schwachstellen enthalten – oder absichtlich bösartig sein. Die OWASP Top 10 führt dafür die Kategorie Software Supply Chain Failures.

RisikoBeispiel
Bekannte SchwachstelleEine Logging-Bibliothek erlaubt das Ausführen von Code über präparierte Log-Einträge (Log4Shell, 2021).
Kompromittiertes PaketDas Konto eines Maintainers wird übernommen, eine neue Version enthält Schadcode, der Secrets stiehlt.
TyposquattingEin Paket mit fast gleichem Namen wie ein bekanntes (Tippfehler) enthält Schadcode.
Verwaistes PaketEine Bibliothek wird nicht mehr gepflegt, Lücken werden nie geschlossen.
  • Software Composition Analysis: Abhängigkeiten automatisch auf bekannte Schwachstellen prüfen (z. B. npm audit, Dependabot, OWASP Dependency-Check) – am besten in der CI-Pipeline.
  • Lockfiles (package-lock.json) einchecken, damit überall exakt dieselben Versionen installiert werden.
  • Regelmäßig aktualisieren – kleine, häufige Updates sind einfacher als ein großer Sprung.
  • Vor dem Hinzufügen prüfen: Wird das Paket gepflegt? Wie viele Abhängigkeiten zieht es nach? Braucht man es wirklich?
  • Eine SBOM (Software Bill of Materials) listet alle enthaltenen Komponenten – damit weiß man bei einer neuen Lücke sofort, ob man betroffen ist.

4 — Security Headers und Security Misconfiguration

Mit wenigen HTTP-Response-Headern aktiviert der Server Schutzfunktionen im Browser:

HeaderWirkung
Content-Security-Policyerlaubte Quellen für Skripte, Styles, Frames … (Lektion 2.6)
Strict-Transport-Security (HSTS)Browser verwendet für diese Domain künftig nur noch HTTPS
X-Content-Type-Options: nosniffBrowser rät den Dateityp nicht selbst (verhindert, dass ein „Bild“ als Skript ausgeführt wird)
Referrer-Policybegrenzt, welche URL-Informationen beim Klick auf externe Links weitergegeben werden
Permissions-Policyschaltet nicht benötigte Browser-Funktionen ab (Kamera, Mikrofon, Standort)
frame-ancestors / X-Frame-OptionsSchutz vor Clickjacking (Lektion 2.6)

Platz 2 der OWASP Top 10 ist Security Misconfiguration – die Anwendung wäre sicher, ist aber falsch eingestellt:

  • Standard-Passwörter (z. B. für Admin-Oberflächen oder Datenbanken) nicht geändert
  • Debug-Modus, Beispielseiten oder Verzeichnislisten in Produktion
  • Header, die Server-Software und Version verraten
  • öffentlich lesbare Cloud-Speicher-Buckets
  • unnötige Dienste, Ports und Funktionen aktiv

5 — Security Logging und Monitoring

Ohne Protokolle bleibt ein Angriff oft monatelang unbemerkt. Security Logging zeichnet sicherheitsrelevante Ereignisse auf, Monitoring wertet sie aus und alarmiert bei Auffälligkeiten.

Protokollieren ✔

  • erfolgreiche und fehlgeschlagene Logins
  • Änderungen an Passwort, E-Mail, MFA
  • verweigerte Zugriffe (403)
  • Admin-Aktionen, Rechteänderungen
  • abgelehnte Eingaben, ungültige Tokens
  • jeweils mit Zeit, Benutzer, IP-Adresse, Correlation ID

Nicht ins Log ✘

  • Passwörter (auch falsche – oft nur vertippt)
  • Session-IDs, Access und Refresh Tokens, API Keys
  • Kreditkarten- und Gesundheitsdaten
  • unnötige personenbezogene Daten (DSGVO: Datenminimierung)
  • Logs zentral und vor Veränderung geschützt speichern – ein Angreifer soll seine Spuren nicht löschen können.
  • Alarme für Muster wie viele fehlgeschlagene Logins, Login aus ungewöhnlichem Land, Massendownload.
  • Log Injection vermeiden: Benutzereingaben im Log kodieren, damit niemand über Zeilenumbrüche gefälschte Einträge erzeugt.
  • Aufbewahrungsdauer festlegen und einhalten.

7 — Umsetzung im FlugBoard

Umgebungsvariablen prüfen

Wie man Secrets in .env.local ablegt, kennst du aus dem React-Kurs (Lektion 3.6). Jetzt sorgen wir dafür, dass ein fehlendes oder zu schwaches Secret sofort auffällt – statt erst, wenn der erste Benutzer TOTP einrichtet:

src/env.ts TypeScript 
import { z } from 'zod';

// Alle Umgebungsvariablen an einer Stelle prüfen: Fehlt ein Secret oder ist
// es zu schwach, startet die Anwendung gar nicht erst (Fail Early).
const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'test', 'production']),
  APP_URL: z.url(),
  DATABASE_PATH: z.string().min(1),
  ENCRYPTION_KEY: z.string().regex(/^[0-9a-f]{64}$/, '32 Byte als Hex, z. B. openssl rand -hex 32'),
  OIDC_ISSUER: z.url(),
  OIDC_CLIENT_ID: z.string().min(1),
  OIDC_CLIENT_SECRET: z.string().min(16),
  OIDC_JWKS_URL: z.url(),
});

export const env = envSchema.parse(process.env);

Statt process.env.ENCRYPTION_KEY verwenden die übrigen Module dann env.ENCRYPTION_KEY – typisiert und garantiert vorhanden.

Security Headers

next.config.ts TypeScript 
import type { NextConfig } from 'next';

const securityHeaders = [
  // künftig nur noch HTTPS (1 Jahr, inkl. Subdomains)
  { key: 'Strict-Transport-Security', value: 'max-age=31536000; includeSubDomains' },
  { key: 'X-Content-Type-Options', value: 'nosniff' },
  { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
  { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
  { key: 'X-Frame-Options', value: 'DENY' }, // für ältere Browser zusätzlich zu frame-ancestors
];

const nextConfig: NextConfig = {
  poweredByHeader: false, // kein "X-Powered-By: Next.js"
  async headers() {
    return [{ source: '/:path*', headers: securityHeaders }];
  },
};

export default nextConfig;

Die Content Security Policy fehlt hier bewusst: Sie braucht einen Nonce pro Anfrage und steht deshalb in der Middleware (Lektion 2.6).

Security Logging

src/lib/security-log.ts TypeScript 
type SecurityEvent =
  | 'login.success'
  | 'login.failure'
  | 'login.rate_limited'
  | 'mfa.enabled'
  | 'access.denied'
  | 'admin.role_changed';

// Diese Felder landen nie im Log – auch nicht versehentlich
const REDACTED_KEYS = ['password', 'token', 'secret', 'session', 'authorization', 'apiKey'];

/** Schreibt ein Sicherheitsereignis als eine JSON-Zeile (für zentrale Auswertung). */
export function logSecurityEvent(
  event: SecurityEvent,
  details: Record<string, string | number | boolean | undefined>,
): void {
  const safe = Object.fromEntries(
    Object.entries(details).map(([key, value]) => [
      key,
      REDACTED_KEYS.some((r) => key.toLowerCase().includes(r.toLowerCase())) ? '[REDACTED]' : value,
    ]),
  );
  // JSON.stringify kodiert Zeilenumbrüche – keine gefälschten Log-Zeilen (Log Injection)
  console.log(JSON.stringify({ time: new Date().toISOString(), type: 'security', event, ...safe }));
}
Verwendung, z. B. in login TypeScript 
if (!user || !valid) {
  logSecurityEvent('login.failure', { email, ip });
  redirect('/login?error=1');
}

Ein Prozessmanager wie systemd (React-Kurs, Lektion 3.6) sammelt diese Zeilen; von dort können sie an ein zentrales Log-System weitergeleitet werden.

Security-Tests mit Playwright

Berechtigungsregeln sind Anforderungen – und Anforderungen testet man. Mit Playwright (React-Kurs, Lektion 3.5) prüfen wir die Regeln aus Lektion 2.4 automatisch:

tests/e2e/access-control.spec.ts TypeScript 
import { expect, test } from '@playwright/test';

// Security-Test: Benutzer B darf die Buchung von Benutzer A nicht sehen (IDOR)
// Voraussetzung: Testdaten mit zwei Benutzern und einer Buchung von A
const BOOKING_OF_A = '3f1c2a9e-0000-4000-8000-000000000001';

async function loginAs(page: import('@playwright/test').Page, email: string) {
  await page.goto('/login');
  await page.getByLabel('E-Mail').fill(email);
  await page.getByLabel('Passwort').fill('ein-langes-testpasswort-123');
  await page.getByRole('button', { name: 'Anmelden' }).click();
  await expect(page).toHaveURL('/konto');
}

test('Besitzerin sieht ihre eigene Buchung', async ({ page }) => {
  await loginAs(page, 'anna@example.com');
  const res = await page.request.get(`/api/bookings/${BOOKING_OF_A}`);
  expect(res.status()).toBe(200);
});

test('fremde Buchung liefert 404', async ({ page }) => {
  await loginAs(page, 'ben@example.com');
  const res = await page.request.get(`/api/bookings/${BOOKING_OF_A}`);
  expect(res.status()).toBe(404);
});

test('ohne Login gibt es 401', async ({ request }) => {
  const res = await request.get(`/api/bookings/${BOOKING_OF_A}`);
  expect(res.status()).toBe(401);
});

test('Passagier kommt nicht in die Benutzerverwaltung', async ({ page }) => {
  await loginAs(page, 'ben@example.com');
  const res = await page.goto('/admin/users');
  expect(res?.status()).toBe(404);
});
💡
Negative Tests

Die meisten Tests prüfen, dass etwas funktioniert. Security-Tests prüfen, dass etwas nicht funktioniert: fremde Daten, fehlende Rechte, ungültige Eingaben. Jede gefundene Lücke bekommt einen Test, damit sie nie wieder auftaucht.

8 — Zusammenfassung des Kurses

ThemaDie wichtigste Regel
Grundlagen (1.1)Never trust the client – alles am Server prüfen.
Passwörter (1.2)Argon2id oder bcrypt, nie Klartext, nie selbst erfunden.
Sessions (1.3)Zufällige ID, Cookie mit Secure, HttpOnly, SameSite; neue ID nach Login.
JWT (1.4)Immer vollständig validieren; kurzlebig; keine Geheimnisse im Payload.
Login in Next.js (2.1)Zufälliges Session-Token, nur gehasht gespeichert; jede Eingabe am Server mit Zod prüfen.
OAuth/OIDC (2.2)Authorization Code + PKCE; für Login das ID Token prüfen.
MFA (2.3)MFA anbieten, Passkeys bevorzugen, Recovery absichern.
Access Control (2.4)Deny by Default, bei jedem Objektzugriff Eigentum prüfen.
Injection (2.5)Prepared Statements, Allowlists, sichere Uploads.
XSS/CSRF (2.6)Output Encoding + CSP; SameSite + CSRF-Token.
APIs (2.7)Validieren, begrenzen, CORS mit Allowlist, keine internen Details in Fehlern.
Secure Development (2.8)Keine Secrets im Code, Abhängigkeiten pflegen, protokollieren, testen.

Häufige Fehler

3 Fehler · zum Aufklappen klicken
Fehler: .env-Datei eingecheckt

Die .env mit dem Datenbank-Passwort wurde mit dem ersten Commit hochgeladen und erst später in .gitignore eingetragen. In der Git-Historie ist sie weiterhin abrufbar.

.gitignore vor dem ersten Commit anlegen; ein bereits veröffentlichtes Secret sofort widerrufen und ersetzen.

Fehler: Warnungen von npm audit ignoriert

Seit Monaten meldet die Pipeline kritische Schwachstellen in Abhängigkeiten, niemand reagiert, weil „ja alles funktioniert“.

Schwachstellen-Meldungen als Teil der Arbeit behandeln: kritische Funde zeitnah beheben, Abhängigkeiten regelmäßig aktualisieren.

Fehler: Kein Log bei fehlgeschlagenen Logins

Ein Angreifer probiert wochenlang Passwörter durch. Weil nur erfolgreiche Logins protokolliert werden, fällt es niemandem auf.

Sicherheitsrelevante Ereignisse – gerade Fehlschläge – protokollieren und bei Auffälligkeiten alarmieren.

Quiz

6 Fragen · zum Aufklappen klicken

Frage 1 Ein API Key wurde versehentlich in ein öffentliches Repository gepusht. Was ist der wichtigste erste Schritt?

Erklärung: Ein veröffentlichtes Secret ist kompromittiert – automatisierte Scanner finden solche Keys oft innerhalb von Minuten. Löschen oder Verstecken hilft nicht, weil Kopien und die Git-Historie existieren. Nur Widerrufen macht den Key wertlos.

Frage 2 Welche Methode analysiert den Quellcode, ohne die Anwendung auszuführen?

Erklärung: Static Application Security Testing untersucht den Code. DAST und Penetrationstests greifen die laufende Anwendung an; Rate Limiting ist eine Schutzmaßnahme, keine Testmethode.

Frage 3 Was gehört nicht in ein Security-Log?

Erklärung: Falsch eingegebene Passwörter sind oft nur vertippte richtige Passwörter – oder das Passwort eines anderen Dienstes. Passwörter, Tokens und Session-IDs gehören nie ins Log.

Frage 4 Wozu dient der Header Strict-Transport-Security (HSTS)?

Erklärung: Mit HSTS merkt sich der Browser, die Seite nur verschlüsselt aufzurufen – auch wenn jemand http:// eintippt. Clickjacking verhindert frame-ancestors, Skriptquellen regelt die CSP.

Frage 5 Welche Aussagen zum OWASP ASVS sind richtig?

Mehrere Antworten sind richtig.

Erklärung: Der ASVS beschreibt detaillierte Anforderungen in drei Levels und dient als Anforderungs- und Prüfliste. Er ist kein Werkzeug, ersetzt die Top 10 nicht (die ist ein Überblick) und ist für alle Webanwendungen gedacht.

Frage 6 Warum steht die Content Security Policy des FlugBoards in der Middleware und nicht in next.config.ts bei den anderen Headern?

Erklärung: Die Header in next.config.ts sind fest. Ein Nonce ist nur sicher, wenn er pro Antwort zufällig ist – deshalb wird die CSP in der Middleware für jede Anfrage neu gebaut.
