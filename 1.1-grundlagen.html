1 — Warum Security in die Webentwicklung gehört

Die meisten erfolgreichen Angriffe auf Webanwendungen brechen nicht durch eine Firewall, sondern nutzen Fehler in der Anwendung selbst: ein fehlender Berechtigungscheck, ein unsicher gespeichertes Passwort, eine Benutzereingabe, die ungeprüft in eine Datenbankabfrage gelangt. Diese Fehler entstehen beim Programmieren – und können auch nur dort behoben werden.

Merksatz

Security ist keine Zusatzfunktion, die man am Ende „einbaut“, sondern eine Eigenschaft des Codes – genauso wie Korrektheit oder Performance.

2 — Authentication vs. Authorization

Die beiden Begriffe klingen ähnlich und werden oft verwechselt. Sie beantworten aber zwei verschiedene Fragen:

Authentication (AuthN)

Wer bist du? Die Anwendung prüft, ob jemand wirklich der ist, für den er sich ausgibt – z. B. durch ein Passwort, einen Code am Handy oder einen Passkey.

Authorization (AuthZ)

Was darfst du? Die Anwendung entscheidet, welche Daten und Funktionen eine bereits bekannte Person verwenden darf.

Beispiel Hotel: An der Rezeption zeigst du deinen Ausweis (Authentication). Du bekommst eine Zimmerkarte, die nur dein Zimmer und den Fitnessraum öffnet, aber nicht die Küche oder fremde Zimmer (Authorization).

Die Authentication kommt immer zuerst: Ohne zu wissen, wer anfragt, kann man nicht entscheiden, was er darf. Umgekehrt gilt aber: Eingeloggt sein heißt nicht, alles zu dürfen.

3 — Schutzziele: Was soll geschützt werden?

Sicherheitsmaßnahmen dienen immer einem oder mehreren Schutzzielen. Die drei klassischen werden nach ihren englischen Anfangsbuchstaben auch CIA-Triade genannt:

SchutzzielBedeutungVerletzung in einer Web-App
Vertraulichkeit (Confidentiality)Nur Berechtigte können Daten lesenFremde lesen Bestellungen oder Gesundheitsdaten
Integrität (Integrity)Daten werden nicht unbemerkt verändertEin Angreifer ändert den Preis im Warenkorb oder die eigene Rolle auf „admin“
Verfügbarkeit (Availability)Das System ist nutzbar, wenn es gebraucht wirdEin Endpunkt wird mit Millionen Anfragen lahmgelegt

Dazu kommt in der Praxis die Nachvollziehbarkeit (Accountability): Man kann feststellen, wer wann was getan hat – etwa durch Security Logging (Lektion 2.8).

4 — Never trust the client

Eine Webanwendung besteht aus Code, der beim Benutzer läuft (Browser, App), und Code, der am Server läuft. Dazwischen liegt eine Vertrauensgrenze (Trust Boundary): Alles, was vom Client kommt, kann der Benutzer – oder ein Angreifer – beliebig verändern.

  • Formularfelder, auch versteckte und deaktivierte Felder
  • URL-Parameter und Pfade
  • Cookies und HTTP-Header
  • JSON-Daten, die ein Frontend an eine API schickt
  • der JavaScript-Code des Frontends selbst – er ist öffentlich lesbar und lässt sich in den DevTools ändern

Angreifer müssen dafür nicht einmal deinen Browser verwenden: Jede HTTP-Anfrage lässt sich mit Werkzeugen wie Postman oder curl frei zusammenstellen.

DO

  • Jede Eingabe am Server prüfen
  • Preise, Rollen und Berechtigungen am Server bestimmen
  • Prüfungen im Frontend nur als Komfort für den Benutzer sehen

DON'T

  • Einen Preis aus einem versteckten Formularfeld übernehmen
  • Admin-Buttons nur ausblenden statt den Zugriff am Server zu sperren
  • Geheimnisse (API-Keys) im Frontend-Code ablegen

5 — Grundprinzipien sicherer Software

PrinzipBedeutung
Defense in DepthMehrere unabhängige Schutzschichten; fällt eine aus, greift die nächste (z. B. Eingabeprüfung und Prepared Statements und eingeschränkter Datenbank-User).
Least PrivilegeJede Person und jede Komponente bekommt nur die Rechte, die sie wirklich braucht (Lektion 2.4).
Secure by DefaultDie Standardeinstellung ist die sichere: Neue Endpunkte sind geschützt, neue Benutzer haben minimale Rechte.
Fail SecurelyIm Fehlerfall wird der Zugriff verweigert, nicht erlaubt; Fehlermeldungen verraten keine internen Details.
Keep it simpleEinfacher, verständlicher Code hat weniger Lücken. Keine eigene Kryptografie erfinden – bewährte Bibliotheken verwenden.

6 — OWASP und die OWASP Top 10

Das Open Worldwide Application Security Project (OWASP) ist eine gemeinnützige Organisation, die frei verfügbare Leitfäden, Werkzeuge und Standards zur Sicherheit von Webanwendungen veröffentlicht. Am bekanntesten ist die OWASP Top 10: eine Liste der zehn kritischsten Risikokategorien für Webanwendungen, die alle paar Jahre auf Basis realer Daten aktualisiert wird.

3 Fehler · zum Aufklappen klicken
Fehler: Security erst am Ende einplanen

Kurz vor dem Release fällt auf, dass jeder eingeloggte Benutzer alle Daten sehen kann. Die Berechtigungsprüfung nachträglich in jede Funktion einzubauen ist aufwendig und fehleranfällig.

Sicherheitsanforderungen (Wer darf was? Welche Daten sind sensibel?) schon beim Entwurf festlegen und von Anfang an mitentwickeln.

Fehler: Prüfung nur im Frontend

Das Formular erlaubt nur Mengen von 1 bis 10 – ein Angreifer schickt per Postman die Menge −5 und erhält eine Gutschrift.

Validierung im Frontend dient nur dem Komfort. Jede Regel muss zusätzlich am Server geprüft werden.

Fehler: „Eingeloggt“ mit „berechtigt“ verwechseln

Die API prüft nur, ob ein gültiges Login vorliegt, aber nicht, ob die angefragten Daten zu diesem Benutzer gehören.

Authentication und Authorization getrennt denken: Nach dem „Wer bist du?“ folgt bei jedem Zugriff das „Darfst du das?“.

Aufgabe 1 AuthN oder AuthZ?

Ordne zu, ob es sich um Authentication oder Authorization handelt, und begründe kurz:

Quiz

4 Fragen · zum Aufklappen klicken

Frage 1 Welche Frage beantwortet die Authorization?

Erklärung: Authorization entscheidet, welche Ressourcen und Funktionen eine bereits authentifizierte Person verwenden darf. „Wer bist du?“ ist die Frage der Authentication, Verschlüsselung und Erreichbarkeit sind andere Themen.

Frage 2 Ein eingeloggter Benutzer ruft eine Admin-Seite auf, für die er keine Rechte hat. Welcher Statuscode passt?

Erklärung: Der Benutzer ist authentifiziert, aber nicht berechtigt – das ist 403. 401 bedeutet trotz des Namens „nicht (gültig) authentifiziert“. Manche Anwendungen antworten bewusst mit 404, um die Existenz der Ressource zu verbergen; der fachlich passende Code ist aber 403.

Frage 3 Ein Angreifer ändert über die DevTools den Preis in einem versteckten Formularfeld von 99 € auf 1 €. Welches Schutzziel ist bedroht und welches Prinzip wurde verletzt?

Erklärung: Die Bestelldaten werden unerlaubt verändert (Integrität). Die Ursache: Der Server vertraut einem Wert, der vom Client kommt. Preise müssen immer am Server aus der Datenbank bestimmt werden.

Frage 4 Was ist die OWASP Top 10?

Erklärung: Die OWASP Top 10 ist ein Awareness-Dokument einer gemeinnützigen Organisation. Sie ist weder Gesetz noch Werkzeug, dient aber weltweit als Orientierung, welche Fehler am häufigsten zu Sicherheitsproblemen führen.
