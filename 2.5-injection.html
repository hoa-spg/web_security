Injection & unsichere Eingaben

Angriffe ca. 60 min Grundlagen

Lernziele

  • Das gemeinsame Prinzip aller Injection-Angriffe erklären
  • Input Validation mit Allowlists korrekt einsetzen und ihre Grenzen kennen
  • SQL Injection beschreiben und mit Prepared Statements verhindern
  • Command Injection und Path Traversal erkennen und vermeiden
  • Risiken von Datei-Uploads nennen und einen sicheren Upload entwerfen
  • Erklären, warum das Deserialisieren nicht vertrauenswürdiger Daten gefährlich ist
  • Datenbankabfragen, Programmaufrufe, Dateipfade und Uploads in Next.js sicher umsetzen

1 — Das Prinzip von Injection

Viele Programme geben Daten an einen Interpreter weiter: an die Datenbank (SQL), an die Shell des Betriebssystems, an das Dateisystem, an den Browser (HTML/JavaScript). Eine Injection entsteht, wenn Benutzereingaben so in einen Befehl eingebaut werden, dass der Interpreter einen Teil der Daten als Befehl versteht.

Bildlich: Ein Formular für eine Paketlieferung hat das Feld „Name“. Jemand schreibt hinein: „Max Muster. Außerdem: Bitte alle Pakete im Lager an mich schicken.“ Ein Mitarbeiter, der den Zettel wörtlich ausführt, ist der Interpreter – Daten und Anweisung lassen sich nicht mehr trennen.

InterpreterAngriffLektion
DatenbankSQL Injection, NoSQL Injectiondiese
Betriebssystem-ShellCommand Injectiondiese
DateisystemPath Traversaldiese
Browser (HTML/JavaScript)Cross-Site Scripting2.6
💡
Die Grundregel

Daten und Befehle immer getrennt an den Interpreter übergeben. Wo das nicht geht, die Daten für genau diesen Interpreter kodieren.

2 — Input Validation

Die erste Verteidigungslinie ist, Eingaben am Server zu prüfen, bevor sie verarbeitet werden:

PrüfungBeispiel
TypMenge ist eine ganze Zahl, nicht „drei“
Länge / BereichBenutzername 3–30 Zeichen, Menge 1–99
FormatPostleitzahl besteht aus 4 Ziffern, Datum ist ein gültiges Datum
Erlaubte WerteSortierung nur nach „name“, „preis“ oder „datum“
SemantikEnddatum liegt nach dem Startdatum, Gutschein gehört zum Konto

Allowlist ✔

Beschreibt, was erlaubt ist. Alles andere wird abgelehnt. Robust, weil unbekannte Angriffe automatisch nicht passen.

Denylist ✘

Versucht, gefährliche Zeichen oder Wörter zu verbieten. Fast immer umgehbar – durch andere Schreibweisen, Kodierungen oder vergessene Fälle.

⚠
Validierung allein reicht nicht

Ein Kommentarfeld muss Apostrophe erlauben („Peter's Pizza“), ein Namensfeld spitze Klammern vielleicht nicht – aber jede Eingabe, die Text erlaubt, kann gefährliche Zeichen enthalten. Input Validation ist eine wichtige Schicht (Defense in Depth); den eigentlichen Schutz liefern die interpreterspezifischen Maßnahmen in den folgenden Abschnitten. Den Begriff Input Sanitization (Eingaben „bereinigen“, etwa Zeichen entfernen) solltest du mit Vorsicht verwenden: Ablehnen ist meist sicherer als stilles Verändern.

3 — SQL Injection

Eine SQL Injection entsteht, wenn eine Anwendung SQL-Befehle durch Zusammensetzen von Zeichenketten mit Benutzereingaben baut. Beispiel Login: Die Anwendung setzt den eingegebenen Benutzernamen direkt in eine Abfrage der Form „suche den Benutzer, dessen Name gleich Eingabe ist und dessen Passwort-Hash gleich … ist“ ein.

Gibt ein Angreifer als Benutzernamen admin' -- ein, beendet der Apostroph den Text, und -- leitet in SQL einen Kommentar ein. Der Rest der Abfrage – die Passwortprüfung – wird damit auskommentiert. Die Datenbank sucht nur noch nach dem Benutzer „admin“, und der Angreifer ist ohne Passwort angemeldet.

Mögliche Folgen einer SQL Injection:

  • Anmeldung ohne Passwort
  • Auslesen beliebiger Tabellen (Kundendaten, Passwort-Hashes)
  • Ändern oder Löschen von Daten
  • je nach Datenbank sogar Ausführen von Betriebssystembefehlen

Auch wenn die Anwendung keine Ergebnisse anzeigt, können Angreifer Daten Zeichen für Zeichen über Ja/Nein-Fragen oder Antwortzeiten erschließen (Blind SQL Injection). Automatisierte Werkzeuge erledigen das in Minuten.

4 — Schutz vor SQL Injection

Prepared Statements (parametrisierte Abfragen)

Bei einem Prepared Statement wird die Abfrage mit Platzhaltern an die Datenbank geschickt und die Werte getrennt davon. Die Datenbank kennt die Struktur der Abfrage, bevor sie die Werte sieht, und behandelt diese ausschließlich als Daten. Ein Apostroph im Benutzernamen ist dann nur ein Apostroph im gesuchten Namen – nie das Ende eines Textes.

MaßnahmeWirkung
Prepared StatementsHauptschutz – Daten und Befehl werden getrennt übertragen
ORM (z. B. Prisma, Hibernate, Entity Framework)verwendet intern Parameter; Vorsicht bei Funktionen für „rohes“ SQL
Allowlist für BezeichnerTabellen- und Spaltennamen (z. B. für Sortierung) lassen sich nicht parametrisieren – nur Werte aus einer festen Liste zulassen
Least PrivilegeDatenbank-User der Anwendung darf nur, was er braucht (Lektion 2.4) – begrenzt den Schaden
Escaping von Sonderzeichenfehleranfällig, nur als letzter Ausweg
ℹ
NoSQL Injection

Auch Dokumentdatenbanken wie MongoDB sind betroffen: Erwartet die Anwendung im JSON-Body ein Passwort als Text, und ein Angreifer schickt stattdessen ein Objekt mit einem Abfrage-Operator wie $ne („ungleich“), passt die Bedingung auf jedes Passwort. Schutz: Typ jedes Feldes prüfen (Text ist Text) und Abfrage-Operatoren nie aus Benutzereingaben übernehmen.

5 — Command Injection

Manche Anwendungen rufen Programme des Betriebssystems auf – etwa ein Netzwerk-Diagnosetool, das ping mit einer vom Benutzer eingegebenen Adresse startet, oder einen Bildkonverter mit dem Dateinamen eines Uploads. Wird dafür eine Shell mit zusammengesetztem Befehl verwendet, können Zeichen wie ;, && oder | weitere Befehle anhängen. Ein Angreifer gibt statt einer IP-Adresse z. B. eine Adresse gefolgt von ; rm -rf / ein.

  • Am besten: keine externen Programme aufrufen, sondern Bibliotheksfunktionen der Programmiersprache verwenden.
  • Falls doch nötig: Programm ohne Shell starten und Argumente als getrennte Liste übergeben – dann werden Sonderzeichen nicht interpretiert.
  • Eingaben streng per Allowlist prüfen (z. B. nur gültige IP-Adressen).
  • Prozess mit minimalen Rechten ausführen.

6 — Path Traversal

Eine Download-Funktion liefert Dateien aus einem Ordner, der Dateiname kommt aus der URL, z. B. /download?file=bericht.pdf. Mit ../ („eine Ebene nach oben“) verlässt ein Angreifer den vorgesehenen Ordner: file=../../config/database.yml liefert die Konfigurationsdatei mit dem Datenbank-Passwort. Diese Schwachstelle heißt Path Traversal (auch Directory Traversal).

  • Keine Dateinamen aus Eingaben verwenden, sondern IDs, die am Server auf einen Dateipfad abgebildet werden.
  • Wenn Dateinamen nötig sind: den Pfad normalisieren (alle ../ auflösen) und prüfen, dass das Ergebnis noch im erlaubten Basisordner liegt.
  • Erlaubte Zeichen und Dateiendungen per Allowlist einschränken.
  • Kodierte Varianten bedenken (%2e%2e%2f ist ../ in URL-Kodierung) – deshalb erst dekodieren und normalisieren, dann prüfen.

7 — File Upload Vulnerabilities

Datei-Uploads (Profilbilder, Dokumente, Abgaben) sind eine der riskantesten Funktionen einer Web-App:

RisikoBeispiel
Ausführbarer CodeEine hochgeladene Skriptdatei (z. B. shell.php) liegt im Webordner und wird beim Aufruf vom Server ausgeführt (Web Shell).
Gefälschter TypDie Datei heißt bild.jpg, der Browser meldet image/jpeg – der Inhalt ist aber HTML oder ein Skript. Beides kommt vom Client und ist frei wählbar.
Aktive InhalteSVG-Bilder und HTML-Dateien können JavaScript enthalten (XSS, Lektion 2.6).
Gefährliche Dateinamen../../index.html überschreibt fremde Dateien (Path Traversal).
RessourcenverbrauchRiesige Dateien oder „Zip-Bomben“, die beim Entpacken Gigabytes ergeben.
SchadsoftwareAndere Benutzer laden die Datei herunter und infizieren sich.

Sicherer Upload – Checkliste

  • Erlaubte Dateiendungen per Allowlist und zusätzlich den tatsächlichen Inhalt prüfen (Dateisignatur, z. B. durch erneutes Einlesen eines Bildes).
  • Datei unter einem zufälligen, serverseitig erzeugten Namen speichern.
  • Außerhalb des Webordners oder in einem separaten Objektspeicher ablegen, nie ausführbar.
  • Größe begrenzen (pro Datei und pro Benutzer).
  • Beim Ausliefern einen festen Content-Type setzen und Dateien möglichst als Download anbieten bzw. von einer eigenen Domain ausliefern.
  • Bei Bedarf auf Schadsoftware scannen.
  • Berechtigungen prüfen: Wer darf welche Datei hochladen und herunterladen? (Lektion 2.4)

8 — Insecure Deserialization

Serialisierung wandelt ein Objekt in eine Byte- oder Textfolge um (zum Speichern oder Übertragen), Deserialisierung baut daraus wieder ein Objekt. Manche Sprachen bieten dafür eigene Binärformate (Java-Serialisierung, Pythons pickle, PHPs unserialize), die beim Einlesen Objekte beliebiger Klassen erzeugen und dabei Code ausführen können.

Kommen solche Daten vom Client – etwa in einem Cookie oder einem versteckten Feld –, kann ein Angreifer präparierte Daten schicken, die beim Deserialisieren beliebigen Code am Server ausführen. Diese Klasse von Schwachstellen ist selten, aber besonders folgenschwer.

  • Keine sprachspezifische Serialisierung für nicht vertrauenswürdige Daten verwenden.
  • Einfache Datenformate wie JSON nutzen und gegen ein Schema validieren.
  • Daten, die der Client nicht verändern darf, signieren (wie beim JWT, Lektion 1.4) oder gleich am Server speichern.

src/lib/flight-search.ts TypeScript 
import { asc, like, sql } from 'drizzle-orm';
import { z } from 'zod';

import { db } from '@/db';
import { flights } from '@/db/schema';

// Allowlist für die Sortierung: Spaltennamen kann man nicht parametrisieren
const SORT_COLUMNS = {
  time: flights.scheduledTime,
  airline: flights.airline,
  airport: flights.airport,
} as const;

const searchSchema = z.object({
  q: z.string().trim().max(50).default(''),
  sort: z.enum(['time', 'airline', 'airport']).default('time'),
});

export function searchFlights(params: { q?: string; sort?: string }) {
  const parsed = searchSchema.safeParse(params);
  const { q, sort } = parsed.success ? parsed.data : { q: '', sort: 'time' as const };

  // Drizzle erzeugt ein Prepared Statement: q wird als Parameter übergeben
  return db.select().from(flights)
    .where(like(flights.airport, `%${q}%`))
    .orderBy(asc(SORT_COLUMNS[sort]))
    .all();
}

// Auch eigenes SQL bleibt sicher, solange Werte über ${} im sql-Template stehen
export function countFlightsByTerminal(terminal: string) {
  return db.get<{ count: number }>(
    sql`SELECT count(*) AS count FROM flights WHERE terminal = ${terminal}`,
  );
}
  • Drizzle-Funktionen wie like und eq erzeugen Prepared Statements – der Suchbegriff wird als Parameter übergeben.
  • Auch im sql-Template von Drizzle werden Werte in ${…} zu Parametern. Gefährlich ist nur sql.raw(), das Text ungeprüft einfügt.
  • Die Sortierspalte lässt sich nicht parametrisieren. Zod lässt nur drei Werte zu (Allowlist), die auf echte Spaltenobjekte abgebildet werden. Ein Wert wie constructor oder __proto__ fällt schon bei der Validierung durch.

10 — Umsetzung: Programme ohne Shell aufrufen

Das Personal soll prüfen können, ob eine Anzeigetafel im Netz erreichbar ist.

So nicht! – Shell mit zusammengesetztem Befehl TypeScript 
import { exec } from 'node:child_process';
exec(`ping -c 1 ${host}`); // host = "8.8.8.8; cat /etc/passwd"
src/app/api/diagnose/route.ts TypeScript 
import { execFile } from 'node:child_process';
import { isIP } from 'node:net';
import { promisify } from 'node:util';

import { NextResponse } from 'next/server';

import { getCurrentUser } from '@/lib/auth';
import { can } from '@/lib/permissions';

const execFileAsync = promisify(execFile);

// GET /api/diagnose?host=10.0.0.5 – Erreichbarkeit einer Anzeigetafel prüfen
export async function GET(request: Request) {
  const user = await getCurrentUser();
  if (!user || !can(user, 'flights:edit')) {
    return NextResponse.json({ error: 'Keine Berechtigung' }, { status: 403 });
  }

  const host = new URL(request.url).searchParams.get('host') ?? '';
  // Allowlist: nur gültige IP-Adressen, keine Namen, keine Sonderzeichen
  if (!isIP(host)) return NextResponse.json({ error: 'Ungültige Adresse' }, { status: 400 });

  try {
    // execFile startet ping OHNE Shell; host ist genau ein Argument
    await execFileAsync('ping', ['-c', '1', '-W', '2', host], { timeout: 5000 });
    return NextResponse.json({ reachable: true });
  } catch {
    return NextResponse.json({ reachable: false });
  }
}

execFile startet das Programm direkt; die Argumente werden als Liste übergeben und nie von einer Shell interpretiert. isIP lässt zusätzlich nur gültige IP-Adressen durch – zwei unabhängige Schichten.

11 — Umsetzung: sicherer Datei-Upload

Passagiere können Reisedokumente hochladen (PDF, PNG, JPEG bis 5 MB).

src/lib/uploads.ts TypeScript 
import path from 'node:path';

// Außerhalb von public/ – nichts davon ist direkt per URL erreichbar
export const UPLOAD_DIR = path.resolve(process.env.UPLOAD_DIR ?? 'storage/uploads');
export const MAX_UPLOAD_BYTES = 5 * 1024 * 1024; // 5 MB

// Allowlist erlaubter Typen mit ihrer Dateisignatur ("Magic Bytes")
const SIGNATURES = [
  { type: 'application/pdf', ext: 'pdf', bytes: [0x25, 0x50, 0x44, 0x46] }, // %PDF
  { type: 'image/png', ext: 'png', bytes: [0x89, 0x50, 0x4e, 0x47] },
  { type: 'image/jpeg', ext: 'jpg', bytes: [0xff, 0xd8, 0xff] },
] as const;

/** Bestimmt den Typ aus dem INHALT der Datei, nicht aus Name oder Content-Type. */
export function detectFileType(data: Buffer) {
  return SIGNATURES.find((sig) => sig.bytes.every((b, i) => data[i] === b)) ?? null;
}

/** Löst einen Dateinamen auf und prüft, dass er im Upload-Ordner bleibt. */
export function resolveInsideUploadDir(fileName: string): string | null {
  const fullPath = path.resolve(UPLOAD_DIR, fileName);
  return fullPath.startsWith(UPLOAD_DIR + path.sep) ? fullPath : null;
}
src/app/api/uploads/route.ts TypeScript 
import { randomUUID } from 'node:crypto';
import { mkdir, writeFile } from 'node:fs/promises';
import path from 'node:path';

import { NextResponse } from 'next/server';

import { getCurrentUser } from '@/lib/auth';
import { detectFileType, MAX_UPLOAD_BYTES, UPLOAD_DIR } from '@/lib/uploads';

// POST /api/uploads – Bordkarte oder Reisedokument hochladen
export async function POST(request: Request) {
  const user = await getCurrentUser();
  if (!user) return NextResponse.json({ error: 'Nicht angemeldet' }, { status: 401 });

  const file = (await request.formData()).get('file');
  if (!(file instanceof File)) {
    return NextResponse.json({ error: 'Keine Datei' }, { status: 400 });
  }
  if (file.size > MAX_UPLOAD_BYTES) {
    return NextResponse.json({ error: 'Datei zu groß' }, { status: 413 });
  }

  const data = Buffer.from(await file.arrayBuffer());
  const type = detectFileType(data);
  if (!type) return NextResponse.json({ error: 'Dateityp nicht erlaubt' }, { status: 415 });

  // Zufälliger Name vom Server – der Originalname wird nie als Pfad verwendet
  const id = `${randomUUID()}.${type.ext}`;
  await mkdir(path.join(UPLOAD_DIR, String(user.id)), { recursive: true });
  await writeFile(path.join(UPLOAD_DIR, String(user.id), id), data);

  return NextResponse.json({ id }, { status: 201 });
}
src/app/api/uploads/[id]/route.ts TypeScript 
import { readFile } from 'node:fs/promises';

import { NextResponse } from 'next/server';

import { getCurrentUser } from '@/lib/auth';
import { detectFileType, resolveInsideUploadDir } from '@/lib/uploads';

interface RouteParams {
  params: Promise<{ id: string }>;
}

// GET /api/uploads/:id – nur eigene Dateien, immer als Download
export async function GET(_request: Request, { params }: RouteParams) {
  const user = await getCurrentUser();
  if (!user) return NextResponse.json({ error: 'Nicht angemeldet' }, { status: 401 });

  const { id } = await params;
  // Allowlist für den Namen + Prüfung, dass der Pfad im Ordner des Benutzers bleibt
  const filePath = /^[0-9a-f-]{36}\.(pdf|png|jpg)$/.test(id)
    ? resolveInsideUploadDir(`${user.id}/${id}`)
    : null;
  if (!filePath) return NextResponse.json({ error: 'Nicht gefunden' }, { status: 404 });

  try {
    const data = await readFile(filePath);
    return new NextResponse(new Uint8Array(data), {
      headers: {
        'Content-Type': detectFileType(data)?.type ?? 'application/octet-stream',
        'Content-Disposition': 'attachment', // herunterladen statt im Browser öffnen
        'X-Content-Type-Options': 'nosniff', // Browser rät den Typ nicht selbst
      },
    });
  } catch {
    return NextResponse.json({ error: 'Nicht gefunden' }, { status: 404 });
  }
}

Größe begrenzenMAX_UPLOAD_BYTES, Antwort 413

kein Path TraversalAllowlist-Regex für die ID und resolveInsideUploadDir

Häufige Fehler

3 Fehler · zum Aufklappen klicken
Fehler: SQL durch Zusammensetzen von Strings

Eine Suchfunktion baut die Abfrage aus festem SQL-Text und dem Suchbegriff zusammen. Mit einem Apostroph im Suchbegriff lässt sich die Abfrage beliebig verändern.

Ausschließlich Prepared Statements bzw. die parametrisierten Funktionen des ORM verwenden – auch für „harmlose“ Abfragen.

Fehler: Denylist statt Allowlist

Die Anwendung entfernt das Wort „SELECT“ und den Text ../ aus Eingaben. Angreifer schreiben „SeLeCt“ oder ....// – nach dem Entfernen entsteht wieder ../.

Erlaubte Eingaben per Allowlist beschreiben und unpassende ablehnen; zusätzlich interpreterspezifisch schützen.

Fehler: Upload in den Webordner

Hochgeladene Dateien werden mit ihrem Originalnamen im öffentlichen Ordner gespeichert. Eine hochgeladene Skriptdatei wird beim Aufruf vom Server ausgeführt.

Zufällige Namen, Speicherung außerhalb des Webordners, Allowlist für Typen und Inhaltsprüfung.

Quiz

6 Fragen · zum Aufklappen klicken

Frage 1 Was haben alle Injection-Angriffe gemeinsam?

Erklärung: Ob SQL, Shell, Dateisystem oder Browser: Die Ursache ist immer, dass Daten und Befehl vermischt werden. HTTPS schützt die Übertragung, nicht die Verarbeitung am Server.

Frage 2 Welche Maßnahme ist der Hauptschutz gegen SQL Injection?

Erklärung: Prepared Statements übertragen Abfragestruktur und Werte getrennt; Werte können die Struktur nicht verändern. Entfernen von Zeichen ist eine fehleranfällige Denylist, Frontend-Begrenzungen sind umgehbar.

Frage 3 Warum ist eine Allowlist robuster als eine Denylist?

Erklärung: Eine Denylist muss jede gefährliche Variante kennen und wird durch andere Schreibweisen oder Kodierungen umgangen. Eine Allowlist beschreibt das Gewünschte; alles andere fällt automatisch heraus.

Frage 4 Eine Download-Funktion erhält file=../../config/secrets.env. Welche Maßnahmen schützen?

Mehrere Antworten sind richtig.

Erklärung: Das ist Path Traversal. IDs statt Dateinamen oder eine Normalisierung mit anschließender Prüfung des Basisordners schützen. Einmaliges Entfernen von ../ lässt sich mit ....// umgehen, die HTTP-Methode spielt keine Rolle.

Frage 5 Welche Aussage zu Datei-Uploads ist richtig?

Erklärung: Content-Type und Dateiname kommen vom Client und sind frei wählbar. Zufällige Namen außerhalb des Webordners verhindern Überschreiben und Ausführen. SVG kann JavaScript enthalten. Den Originalnamen kann man in der Datenbank speichern und nur zur Anzeige verwenden.

Frage 6 Welche Drizzle-Abfrage ist anfällig für SQL Injection, wenn q vom Benutzer kommt?

Erklärung: eq, like und Werte im sql-Template werden als Parameter übergeben. sql.raw fügt den fertigen Text ungeprüft ein – hier wurde der Wert vorher per JavaScript-Template-String eingesetzt, genau wie beim klassischen Zusammensetzen.
