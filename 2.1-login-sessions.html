2 — Datenmodell: Benutzer und Sessions

Zur bestehenden Tabelle flights kommen zwei neue Tabellen: users speichert E-Mail, Passwort-Hash und Rolle, sessions ist unser Session-Store aus Lektion 1.3.

src/db/schema.ts TypeScript 
import { integer, sqliteTable, text } from 'drizzle-orm/sqlite-core';

// Bestehende Tabelle aus dem React-Kurs (gekürzt)
export const flights = sqliteTable('flights', {
  id: integer('id').primaryKey(),
  flightNumber: text('flight_number').notNull(),
  airline: text('airline').notNull(),
  airport: text('airport').notNull(),
  terminal: text('terminal').notNull(),
  scheduledTime: text('scheduled_time').notNull(),
});

export const users = sqliteTable('users', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  email: text('email').notNull().unique(),
  passwordHash: text('password_hash').notNull(),
  role: text('role', { enum: ['passenger', 'staff', 'admin'] })
    .notNull()
    .default('passenger'),
});

export const sessions = sqliteTable('sessions', {
  // SHA-256-Hash des Session-Tokens – das Token selbst steht nur im Cookie
  id: text('id').primaryKey(),
  userId: integer('user_id')
    .notNull()
    .references(() => users.id, { onDelete: 'cascade' }),
  expiresAt: integer('expires_at', { mode: 'timestamp' }).notNull(),
});
  • role ist auf drei Werte beschränkt und standardmäßig passenger – neue Konten haben minimale Rechte (Secure by Default).
  • sessions.id enthält nicht das Session-Token selbst, sondern dessen Hash. Wird die Datenbank gestohlen, kann niemand mit den Einträgen eine Session übernehmen – dasselbe Prinzip wie bei Passwörtern.
  • onDelete: 'cascade' löscht beim Entfernen eines Benutzers auch alle seine Sessions.

3 — Passwörter hashen mit Argon2id

Das Paket @node-rs/argon2 implementiert Argon2 (Lektion 1.2). Es erzeugt den Salt selbst und schreibt Verfahren, Parameter und Salt in den Hash-String – wir müssen nur die Parameter wählen.

src/lib/password.ts TypeScript 
import { hash, verify } from '@node-rs/argon2';

// Argon2id (Standard der Bibliothek) mit den Mindestwerten
// aus dem OWASP Password Storage Cheat Sheet: 19 MiB Speicher, 2 Durchläufe
const OPTIONS = { memoryCost: 19456, timeCost: 2, parallelism: 1 };

export function hashPassword(password: string): Promise<string> {
  // Salt erzeugt die Bibliothek selbst und speichert ihn im Hash-String
  return hash(password, OPTIONS);
}

export function verifyPassword(passwordHash: string, password: string): Promise<boolean> {
  return verify(passwordHash, password);
}

// Wird geprüft, wenn es den Benutzer gar nicht gibt – so dauert ein
// Login mit unbekannter E-Mail-Adresse genauso lange wie mit bekannter.
export const dummyHash = hashPassword('dummy-password-for-timing');

Ein gespeicherter Hash sieht etwa so aus – alles, was zum Prüfen nötig ist, steht darin:

users.password_hash Text 
$argon2id$v=19$m=19456,t=2,p=1$Yk4wVnlr…(Salt)…$3vPq…(Hash)…

dummyHash brauchen wir beim Login: Gibt es die E-Mail-Adresse nicht, prüfen wir trotzdem einen Hash. Sonst wäre die Antwort für unbekannte Adressen messbar schneller, und Angreifer könnten über die Antwortzeit herausfinden, welche Konten existieren (User Enumeration).

4 — Neue Werkzeuge: node:crypto und cookies()

Sichere Zufallswerte und Hashes

Das eingebaute Node-Modul node:crypto liefert alles, was wir für Session-Tokens brauchen:

FunktionZweck
randomBytes(32)32 Bytes aus einem kryptografisch sicheren Zufallsgenerator – im Gegensatz zu Math.random(), das vorhersagbar ist
.toString('base64url')Bytes als URL- und Cookie-taugliche Zeichenkette
createHash('sha256')schneller Hash – für zufällige Tokens mit 256 Bit genau richtig (für Passwörter nicht, siehe Lektion 1.2)

Cookies in Next.js

Die Funktion cookies() aus next/headers gibt Zugriff auf die Cookies der aktuellen Anfrage. Sie ist async und funktioniert nur am Server.

MethodeErlaubt in
get(name), has(name)Server Components, Server Actions, Route Handlers
set(name, value, options), delete(name)nur Server Actions und Route Handlers – eine Server Component darf keine Cookies setzen

5 — Sessions erzeugen, prüfen und beenden

src/lib/session.ts TypeScript 
import { createHash, randomBytes } from 'node:crypto';

import { eq } from 'drizzle-orm';
import { cookies } from 'next/headers';

import { db } from '@/db';
import { sessions, users } from '@/db/schema';

const SESSION_COOKIE = 'session';
const SESSION_DURATION_MS = 8 * 60 * 60 * 1000; // absolute Laufzeit: 8 Stunden

function hashToken(token: string): string {
  return createHash('sha256').update(token).digest('hex');
}

/** Legt nach einem erfolgreichen Login eine neue Session an. */
export async function createSession(userId: number): Promise<void> {
  // 32 zufällige Bytes = 256 Bit, kryptografisch sicher erzeugt
  const token = randomBytes(32).toString('base64url');
  const expiresAt = new Date(Date.now() + SESSION_DURATION_MS);

  await db.insert(sessions).values({ id: hashToken(token), userId, expiresAt });

  const cookieStore = await cookies();
  cookieStore.set(SESSION_COOKIE, token, {
    httpOnly: true, // für JavaScript im Browser unsichtbar
    secure: process.env.NODE_ENV === 'production', // nur über HTTPS
    sameSite: 'lax', // nicht bei Cross-Site-POSTs mitschicken
    path: '/',
    expires: expiresAt,
  });
}

/** Liefert den angemeldeten Benutzer oder null. */
export async function getSessionUser() {
  const cookieStore = await cookies();
  const token = cookieStore.get(SESSION_COOKIE)?.value;
  if (!token) return null;

  const row = db
    .select({
      // nur die Felder, die die Anwendung braucht – kein Passwort-Hash
      user: { id: users.id, email: users.email, role: users.role },
      expiresAt: sessions.expiresAt,
    })
    .from(sessions)
    .innerJoin(users, eq(sessions.userId, users.id))
    .where(eq(sessions.id, hashToken(token)))
    .get();

  if (!row || row.expiresAt.getTime() < Date.now()) return null;
  return row.user;
}

/** Beendet die Session am Server und im Browser. */
export async function deleteSession(): Promise<void> {
  const cookieStore = await cookies();
  const token = cookieStore.get(SESSION_COOKIE)?.value;
  if (token) {
    await db.delete(sessions).where(eq(sessions.id, hashToken(token)));
  }
  cookieStore.delete(SESSION_COOKIE);
}

Jede Zeile setzt eine Regel aus Lektion 1.3 um:

CodeRegel
randomBytes(32)Session-ID zufällig, mindestens 128 Bit, ohne Bedeutung
httpOnly: trueDiebstahl per XSS verhindern
secure: …productionnur über HTTPS (lokal läuft der Dev-Server mit HTTP)
sameSite: 'lax'Schutz vor Cross-Site-Anfragen
expires + Prüfung von expiresAtAbsolute Timeout – am Server geprüft, nicht nur im Browser
db.delete(sessions) in deleteSessionLogout beendet die Session am Server
select({ user: { id, email, role } })Passwort-Hash verlässt die Datenbankschicht nicht

Damit Seiten bequem auf den angemeldeten Benutzer zugreifen können, kommt eine kleine Hilfsdatei dazu:

src/lib/auth.ts TypeScript 
import { redirect } from 'next/navigation';
import { cache } from 'react';

import { getSessionUser } from './session';

// cache: pro Anfrage nur einmal in der Datenbank nachsehen,
// auch wenn mehrere Komponenten getCurrentUser() aufrufen
export const getCurrentUser = cache(getSessionUser);

export type CurrentUser = NonNullable<Awaited<ReturnType<typeof getSessionUser>>>;

/** Für geschützte Seiten: ohne Login geht es zur Anmeldung. */
export async function requireUser(): Promise<CurrentUser> {
  const user = await getCurrentUser();
  if (!user) redirect('/login');
  return user;
}

cache aus React merkt sich das Ergebnis für die Dauer einer Anfrage: Rufen Layout, Seite und mehrere Komponenten getCurrentUser() auf, wird die Datenbank trotzdem nur einmal gefragt. redirect() kennst du aus dem React-Kurs (Lektion 3.4).

6 — Eingaben prüfen mit Zod

Die Prüfung im Browser (required, minLength) ist nur Komfort – jeder kann eine Server Action auch ohne unser Formular aufrufen. Am Server verwenden wir Zod, eine Bibliothek, mit der man ein Schema für erwartete Daten beschreibt und Eingaben dagegen prüft:

  • z.object({ … }) beschreibt ein Objekt mit Feldern; z.string().min(15).max(128) einen Text mit Längengrenzen, z.email() eine E-Mail-Adresse.
  • schema.safeParse(daten) wirft keinen Fehler, sondern liefert { success: true, data } oder { success: false, error }.
  • Nach erfolgreicher Prüfung ist data korrekt typisiert – TypeScript kennt die Felder.

Zod begleitet uns durch den ganzen Teil 2 (Allowlists in 2.4, Request Validation in 2.7).

7 — Registrierung, Login und Logout

src/actions/auth-actions.ts TypeScript 
'use server';

import { eq } from 'drizzle-orm';
import { redirect } from 'next/navigation';
import { z } from 'zod';

import { db } from '@/db';
import { users } from '@/db/schema';
import { dummyHash, hashPassword, verifyPassword } from '@/lib/password';
import { createSession, deleteSession } from '@/lib/session';

const registerSchema = z.object({
  email: z.email().max(254),
  password: z.string().min(15).max(128),
});

function readCredentials(formData: FormData) {
  return {
    email: String(formData.get('email') ?? '').trim().toLowerCase(),
    password: String(formData.get('password') ?? ''),
  };
}

export async function register(formData: FormData) {
  const parsed = registerSchema.safeParse(readCredentials(formData));
  if (!parsed.success) redirect('/register?error=invalid');

  const { email, password } = parsed.data;
  const existing = db.select({ id: users.id }).from(users)
    .where(eq(users.email, email)).get();
  if (existing) redirect('/register?error=invalid');

  const passwordHash = await hashPassword(password);
  const user = db.insert(users).values({ email, passwordHash })
    .returning({ id: users.id }).get();

  await createSession(user.id);
  redirect('/konto');
}

export async function login(formData: FormData) {
  const { email, password } = readCredentials(formData);
  const user = db.select({ id: users.id, passwordHash: users.passwordHash })
    .from(users).where(eq(users.email, email)).get();

  // Auch bei unbekannter E-Mail einen Hash prüfen (gleiche Antwortzeit)
  const valid = await verifyPassword(user?.passwordHash ?? (await dummyHash), password);

  // Eine Meldung für alle Fehlerfälle – keine User Enumeration
  if (!user || !valid) redirect('/login?error=1');

  await createSession(user.id); // immer eine NEUE Session (gegen Fixation)
  redirect('/konto');
}

export async function logout() {
  await deleteSession();
  redirect('/login');
}
  • Einheitliche Fehlermeldungen: Login kennt nur error=1, egal ob die E-Mail fehlt oder das Passwort falsch ist.
  • Gleiche Antwortzeit: Gibt es den Benutzer nicht, wird gegen dummyHash geprüft.
  • Neue Session bei jedem Login: createSession erzeugt immer ein neues Token – Session Fixation ist ausgeschlossen.
  • E-Mail normalisieren: trim().toLowerCase(), damit „Anna@Example.com“ und „anna@example.com“ dasselbe Konto sind.
  • redirect() beendet die Funktion sofort (Rückgabetyp never) – deshalb weiß TypeScript nach if (!user || !valid) redirect(…), dass user existiert.
⚠
Registrierung und User Enumeration

Auch die Registrierung verrät, ob eine Adresse schon existiert. Unsere Meldung ist neutral gehalten („Bitte Eingaben prüfen“). Ganz verhindern lässt sich das nur, wenn die Bestätigung per E-Mail erfolgt: „Wir haben dir eine Nachricht geschickt“ – bei bestehenden Konten mit dem Hinweis, dass bereits ein Konto existiert.

8 — Login-Seite und geschützte Seite

src/app/login/page.tsx TypeScript 
import Link from 'next/link';

import { login } from '@/actions/auth-actions';

interface LoginPageProps {
  searchParams: Promise<{ error?: string }>;
}

export default async function LoginPage({ searchParams }: LoginPageProps) {
  const { error } = await searchParams;

  return (
    <main>
      <h1>Anmelden</h1>
      {error && <p role="alert">E-Mail oder Passwort ist falsch.</p>}
      <form action={login}>
        <label>
          E-Mail
          <input name="email" type="email" autoComplete="username" required />
        </label>
        <label>
          Passwort
          <input name="password" type="password" autoComplete="current-password" required />
        </label>
        <button type="submit">Anmelden</button>
      </form>
      <p><Link href="/register">Konto erstellen</Link></p>
    </main>
  );
}

autoComplete="username" und "current-password" helfen Passwort-Managern – ein Sicherheitsgewinn, denn Passwort-Manager erzeugen lange, zufällige Passwörter und füllen sie nur auf der echten Domain aus. Die Registrierungsseite src/app/register/page.tsx ist analog aufgebaut (mit "new-password").

Häufige Fehler

3 Fehler · zum Aufklappen klicken
Fehler: Cookie in einer Server Component setzen

Die Konto-Seite soll die Session verlängern und ruft cookies().set(…) auf. Next.js wirft den Fehler „Cookies can only be modified in a Server Action or Route Handler“.

Cookies nur in Server Actions oder Route Handlers setzen; Server Components lesen sie nur.

Fehler: Token im Klartext in der Datenbank

Die Tabelle sessions speichert das Token direkt. Wer ein Datenbank-Backup in die Hände bekommt, kann sich als jeder angemeldete Benutzer ausgeben.

Nur den SHA-256-Hash speichern und beim Prüfen das Token aus dem Cookie hashen.

Fehler: Validierung nur im Formular

Das Passwortfeld hat minLength={15}, die Server Action prüft nichts. Mit den DevTools entfernt man das Attribut und registriert sich mit „123“.

Jede Regel am Server prüfen – hier mit dem Zod-Schema in der Server Action.

Quiz

6 Fragen · zum Aufklappen klicken

Frage 1 Warum speichert die Tabelle sessions den SHA-256-Hash des Tokens statt des Tokens selbst?

Erklärung: Wie beim Passwort gilt: Was in der Datenbank steht, kann bei einem Leck in falsche Hände geraten. Mit dem Hash allein lässt sich kein gültiges Cookie bauen. Für zufällige 256-Bit-Tokens genügt ein schneller Hash wie SHA-256 – ein langsames Verfahren wie Argon2 ist nur für erratbare Passwörter nötig.

Frage 2 Warum verwendet createSession randomBytes statt Math.random()?

Erklärung: Math.random() ist für Spiele und Animationen gedacht; seine Werte lassen sich unter Umständen vorhersagen. Für Session-Tokens, Reset-Links und Ähnliches braucht man einen kryptografisch sicheren Zufallsgenerator wie randomBytes oder crypto.randomUUID().

Frage 3 Wozu prüft login gegen dummyHash, wenn es den Benutzer nicht gibt?

Erklärung: Ohne Dummy-Prüfung würde die Antwort für unbekannte Adressen sofort kommen, für bekannte erst nach der Argon2-Berechnung. Über diesen Zeitunterschied ließen sich gültige Konten ermitteln (User Enumeration), obwohl die Fehlermeldung gleich ist.

Frage 4 Wo darf in Next.js cookies().set(…) aufgerufen werden?

Mehrere Antworten sind richtig.

Erklärung: Cookies werden über die HTTP-Antwort gesetzt. Server Components dürfen sie nur lesen, weil ihre Ausgabe bereits gestreamt werden kann. Client Components laufen im Browser – ein dort gesetztes Cookie könnte ohnehin nicht HttpOnly sein.

Frage 5 Welche Zeile verhindert Session Fixation?

Erklärung: Session Fixation funktioniert nur, wenn eine vorher bekannte ID nach dem Login weiterverwendet wird. Da jedes Login ein neues, zufälliges Token erzeugt, ist eine untergeschobene ID wertlos. Die anderen Zeilen setzen Timeout, CSRF-Schutz und Eingabeprüfung um.

Frage 6 Welche Bausteine des FlugBoard-Logins sind Next.js-spezifisch und sehen in einem anderen Backend (z. B. Hono) anders aus?

Mehrere Antworten sind richtig.

Erklärung: Cookie-Zugriff und Server Actions sind Funktionen von Next.js; in Hono verwendet man setCookie und normale POST-Routen und prüft den Origin selbst. Argon2 und Zod sind gewöhnliche Bibliotheken, die in jedem JavaScript-Backend gleich funktionieren.
