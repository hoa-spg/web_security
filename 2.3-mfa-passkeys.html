1 — Authentifizierungsfaktoren

Es gibt drei Kategorien, mit denen man seine Identität belegen kann:

KategorieBeschreibungBeispiele
Wissenetwas, das du weißtPasswort, PIN
Besitzetwas, das du hastSmartphone mit Authenticator-App, Security Key, Chipkarte
Inhärenz (Sein)etwas, das du bistFingerabdruck, Gesichtserkennung
  • Multi-Factor Authentication (MFA) kombiniert Faktoren aus mindestens zwei verschiedenen Kategorien.
  • Two-Factor Authentication (2FA) ist der häufigste Spezialfall mit genau zwei Faktoren, z. B. Passwort + Code aus einer App.
  • Passwort + Sicherheitsfrage ist keine MFA – beides ist Wissen.

Selbst ein einfacher zweiter Faktor verhindert den Großteil automatisierter Kontoübernahmen durch Credential Stuffing (Lektion 1.2), weil ein erbeutetes Passwort allein nicht mehr reicht.

Number Matching

Bei Push-Verfahren zeigt die Login-Seite eine Zahl an, die der Benutzer in der App eintippen oder auswählen muss. Wer eine Anfrage nicht selbst ausgelöst hat, kennt die Zahl nicht – das stoppt MFA-Fatigue-Angriffe.

3 — TOTP: Time-based One-Time Password

TOTP (RFC 6238) ist das Verfahren hinter Authenticator-Apps wie Google Authenticator, Microsoft Authenticator oder Aegis.

Einrichtung

  1. Der Server erzeugt ein zufälliges gemeinsames Geheimnis (Shared Secret) für den Benutzer.
  2. Er zeigt es als QR-Code an, den die Authenticator-App scannt.
  3. Zur Bestätigung gibt der Benutzer einen ersten Code ein. Erst dann ist TOTP aktiv.
  4. Der Server speichert das Geheimnis – verschlüsselt, da er es zum Prüfen im Klartext braucht.

Anmeldung

App und Server berechnen unabhängig voneinander aus dem Geheimnis und der aktuellen Zeit (in 30-Sekunden-Schritten) einen sechsstelligen Code. Stimmen die Codes überein, besitzt der Benutzer das Gerät mit dem Geheimnis. Eine Internetverbindung braucht die App dafür nicht.

  • Der Server akzeptiert meist auch den vorigen und nächsten Zeitschritt, weil Uhren leicht abweichen.
  • Ein bereits verwendeter Code wird kein zweites Mal akzeptiert.
  • Fehlversuche werden begrenzt (Rate Limiting) – sechs Ziffern sind nur eine Million Möglichkeiten.

4 — Warum Einmalcodes nicht vor Phishing schützen

Moderne Phishing-Kits arbeiten als Adversary-in-the-Middle:

  1. Das Opfer landet auf login-micros0ft.example, einer täuschend echten Kopie.
  2. Die Phishing-Seite reicht Benutzername und Passwort in Echtzeit an die echte Seite weiter.
  3. Die echte Seite fragt nach dem TOTP-Code – die Phishing-Seite fragt das Opfer ebenso.
  4. Das Opfer tippt den Code ein, die Phishing-Seite meldet sich damit an und erbeutet das Session-Cookie.

Das Problem: Ein Mensch erkennt den Unterschied zwischen echter und gefälschter Domain oft nicht, und ein Code funktioniert unabhängig davon, wo er eingegeben wird. Phishing-resistent ist ein Verfahren dann, wenn die Anmeldung kryptografisch an die echte Domain gebunden ist und der Browser – nicht der Mensch – die Domain prüft. Genau das leistet WebAuthn.

5 — WebAuthn und FIDO2

WebAuthn ist ein W3C-Standard, der eine Browser-Schnittstelle für Anmeldungen mit Public-Key-Kryptografie definiert. Zusammen mit dem Protokoll CTAP (Kommunikation mit externen Security Keys) bildet er FIDO2, entwickelt von der FIDO Alliance (u. a. Apple, Google, Microsoft).

BeteiligterRolle
Relying Partydeine Webanwendung (Server)
Browserstellt die WebAuthn-Schnittstelle bereit und prüft die Domain
Authenticatorerzeugt und verwahrt die Schlüssel: im Gerät eingebaut (Platform Authenticator: Windows Hello, Touch ID, Android) oder extern (Roaming Authenticator: USB-/NFC-Security-Key)

Registrierung

  1. Der Server schickt eine zufällige Challenge.
  2. Der Authenticator erzeugt ein neues Schlüsselpaar nur für diese Domain.
  3. Der öffentliche Schlüssel geht an den Server und wird beim Konto gespeichert. Der private Schlüssel verlässt den Authenticator nie.

Anmeldung

  1. Der Server schickt eine neue Challenge.
  2. Der Benutzer bestätigt am Authenticator, meist per Fingerabdruck, Gesicht oder Geräte-PIN (User Verification, findet lokal statt – biometrische Daten verlassen das Gerät nicht).
  3. Der Authenticator signiert die Challenge zusammen mit der vom Browser übermittelten Domain.
  4. Der Server prüft die Signatur mit dem gespeicherten öffentlichen Schlüssel.
💡
Warum das so sicher ist
  • Phishing-resistent: Der Browser gibt die echte Domain an den Authenticator weiter. Auf login-micros0ft.example existiert kein passender Schlüssel.
  • Kein Geheimnis am Server: Wird die Datenbank gestohlen, erbeuten Angreifer nur öffentliche Schlüssel – damit kann man sich nicht anmelden.
  • Kein Wiederverwenden: Jede Website bekommt ein eigenes Schlüsselpaar, jede Anmeldung eine neue Challenge.

6 — Passkeys: passwortlose Anmeldung

Ein Passkey ist ein WebAuthn-Schlüssel, der das Passwort komplett ersetzt. Der Benutzer wählt nur noch sein Konto aus und bestätigt mit Fingerabdruck, Gesicht oder PIN. Weil dabei Besitz (Gerät mit Schlüssel) und Inhärenz bzw. Wissen (Biometrie bzw. PIN) zusammenkommen, gilt die Anmeldung mit einem Passkey bereits als Multi-Faktor.

ArtBeschreibungVor- und Nachteil
Synchronisierte Passkeyswerden über den Passwort-Manager des Betriebssystems oder einen Drittanbieter (iCloud-Schlüsselbund, Google Passwortmanager, 1Password …) auf alle Geräte des Benutzers verteiltkomfortabel, Geräteverlust kein Problem – Sicherheit hängt am Konto des Sync-Anbieters
Gerätegebundene Passkeysliegen nur auf einem Gerät, z. B. einem Security Keyhöchste Sicherheit (für Admins, Hochrisikokonten) – bei Verlust Ersatz nötig
  • Auf einem fremden Gerät kann man sich anmelden, indem man einen QR-Code mit dem Handy scannt; die Nähe wird per Bluetooth geprüft.
  • Für Benutzer wirkt ein Passkey wie „Entsperren des Handys“ – einfacher als jedes Passwort.
  • Für Entwickler: WebAuthn-Bibliotheken für den Server verwenden, das Protokoll nicht selbst implementieren.

7 — Account Recovery und Einführung

Jede Anmeldung ist nur so sicher wie der Weg, auf dem man sie umgehen kann. Wenn „Handy verloren“ dazu führt, dass ein Anruf beim Support oder ein SMS-Code reicht, ist das die eigentliche Schwachstelle.

  • Recovery Codes: Bei der Einrichtung einmalige Wiederherstellungscodes anzeigen, die der Benutzer offline aufbewahrt.
  • Mehrere Faktoren registrieren lassen (z. B. zwei Passkeys auf verschiedenen Geräten).
  • Änderungen an der MFA (Faktor entfernen, neue E-Mail) nur nach erneuter Anmeldung und mit Benachrichtigung.
  • Step-up Authentication: MFA nicht nur beim Login, sondern erneut vor kritischen Aktionen (Überweisung, Admin-Funktion) verlangen.
  • MFA verpflichtend mindestens für Administratoren und Konten mit Zugriff auf sensible Daten.

Das TOTP-Geheimnis verschlüsseln

Anders als ein Passwort muss der Server das TOTP-Geheimnis im Klartext kennen, um Codes zu berechnen – Hashen geht also nicht. Wir speichern es deshalb verschlüsselt mit AES-256-GCM. Der Schlüssel steht nicht in der Datenbank, sondern in der Umgebungsvariable ENCRYPTION_KEY (Lektion 2.8). GCM erkennt zusätzlich, ob der Geheimtext manipuliert wurde.

src/lib/crypto.ts TypeScript 
import { createCipheriv, createDecipheriv, randomBytes } from 'node:crypto';

// 32 Byte Schlüssel als 64 Hex-Zeichen, z. B. erzeugt mit: openssl rand -hex 32
const key = Buffer.from(process.env.ENCRYPTION_KEY ?? '', 'hex');

/** Verschlüsselt mit AES-256-GCM; Ergebnis: iv.tag.daten (base64url). */
export function encrypt(plain: string): string {
  const iv = randomBytes(12);
  const cipher = createCipheriv('aes-256-gcm', key, iv);
  const data = Buffer.concat([cipher.update(plain, 'utf8'), cipher.final()]);
  return [iv, cipher.getAuthTag(), data].map((b) => b.toString('base64url')).join('.');
}

export function decrypt(encrypted: string): string {
  const [iv, tag, data] = encrypted.split('.').map((s) => Buffer.from(s, 'base64url'));
  const decipher = createDecipheriv('aes-256-gcm', key, iv);
  decipher.setAuthTag(tag); // erkennt Manipulationen am Geheimtext
  return Buffer.concat([decipher.update(data), decipher.final()]).toString('utf8');
}

TOTP erzeugen und prüfen

src/lib/totp.ts TypeScript 
import { authenticator } from 'otplib';
import QRCode from 'qrcode';

// vorigen und nächsten 30-Sekunden-Schritt akzeptieren (Uhrabweichung)
authenticator.options = { window: 1 };

export function createTotpSecret(): string {
  return authenticator.generateSecret(); // zufällig, Base32
}

/** QR-Code (als Data-URL) für die Authenticator-App. */
export function totpQrCode(email: string, secret: string): Promise<string> {
  const uri = authenticator.keyuri(email, 'FlugBoard', secret);
  return QRCode.toDataURL(uri);
}

export function verifyTotp(token: string, secret: string): boolean {
  return /^\d{6}$/.test(token) && authenticator.verify({ token, secret });
}

export const TOTP_SETUP_COOKIE = 'totp_setup';

keyuri erzeugt eine Adresse der Form otpauth://totp/FlugBoard:anna@…?secret=…, die die Authenticator-App aus dem QR-Code liest.

Einrichtung und zweiter Login-Schritt

Die Einrichtung läuft in zwei Schritten: Ein neues Geheimnis wird erzeugt und (verschlüsselt, zehn Minuten gültig) im Cookie zwischengespeichert; erst wenn der Benutzer einen passenden Code eingibt, wird es dauerhaft gespeichert. So kann sich niemand mit einer halb eingerichteten App aussperren.

src/actions/mfa-actions.ts TypeScript 
'use server';

import { eq } from 'drizzle-orm';
import { cookies } from 'next/headers';
import { redirect } from 'next/navigation';

import { db } from '@/db';
import { users } from '@/db/schema';
import { requireUser } from '@/lib/auth';
import { decrypt, encrypt } from '@/lib/crypto';
import { getSession, markMfaVerified } from '@/lib/session';
import { createTotpSecret, TOTP_SETUP_COOKIE, verifyTotp } from '@/lib/totp';

/** Schritt 1: neues Geheimnis erzeugen und verschlüsselt zwischenspeichern. */
export async function startTotpSetup() {
  await requireUser();
  (await cookies()).set(TOTP_SETUP_COOKIE, encrypt(createTotpSecret()), {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    path: '/konto/mfa',
    maxAge: 10 * 60,
  });
  redirect('/konto/mfa');
}

/** Schritt 2: erster Code muss zum neuen Geheimnis passen. */
export async function confirmTotpSetup(formData: FormData) {
  const user = await requireUser();
  const cookieStore = await cookies();
  const pending = cookieStore.get(TOTP_SETUP_COOKIE)?.value;
  const token = String(formData.get('token') ?? '');

  if (!pending || !verifyTotp(token, decrypt(pending))) redirect('/konto/mfa?error=1');

  // in der Datenbank bleibt das Geheimnis verschlüsselt
  await db.update(users).set({ totpSecret: pending }).where(eq(users.id, user.id));
  cookieStore.delete(TOTP_SETUP_COOKIE);
  redirect('/konto');
}

/** Zweiter Schritt beim Login. */
export async function verifyMfaLogin(formData: FormData) {
  const session = await getSession();
  if (!session) redirect('/login');

  const row = db.select({ totpSecret: users.totpSecret }).from(users)
    .where(eq(users.id, session.user.id)).get();
  const token = String(formData.get('token') ?? '');

  if (!row?.totpSecret || !verifyTotp(token, decrypt(row.totpSecret))) {
    redirect('/login/mfa?error=1');
  }
  await markMfaVerified();
  redirect('/konto');
}

Session mit zwei Stufen

Nach dem Passwort ist ein Benutzer mit TOTP erst „halb“ angemeldet. Die Session bekommt deshalb das Feld mfaVerified. getSessionUser() – und damit requireUser() – liefert den Benutzer nur, wenn es true ist; alle bisher geschützten Seiten bleiben also automatisch gesperrt, bis der Code eingegeben wurde.

src/lib/session.ts TypeScript 
import { createHash, randomBytes } from 'node:crypto';

import { eq } from 'drizzle-orm';
import { cookies } from 'next/headers';

import { db } from '@/db';
import { sessions, users } from '@/db/schema';

const SESSION_COOKIE = 'session';
const SESSION_DURATION_MS = 8 * 60 * 60 * 1000; // absolute Laufzeit: 8 Stunden

function hashToken(token: string): string {
  return createHash('sha256').update(token).digest('hex');
}

async function currentTokenHash(): Promise<string | null> {
  const token = (await cookies()).get(SESSION_COOKIE)?.value;
  return token ? hashToken(token) : null;
}

/** Legt nach einem erfolgreichen Login eine neue Session an. */
export async function createSession(userId: number, mfaVerified = true): Promise<void> {
  const token = randomBytes(32).toString('base64url');
  const expiresAt = new Date(Date.now() + SESSION_DURATION_MS);

  await db.insert(sessions).values({ id: hashToken(token), userId, expiresAt, mfaVerified });

  const cookieStore = await cookies();
  cookieStore.set(SESSION_COOKIE, token, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'lax',
    path: '/',
    expires: expiresAt,
  });
}

/** Liefert Benutzer und MFA-Status der aktuellen Session oder null. */
export async function getSession() {
  const id = await currentTokenHash();
  if (!id) return null;

  const row = db
    .select({
      user: { id: users.id, email: users.email, role: users.role },
      expiresAt: sessions.expiresAt,
      mfaVerified: sessions.mfaVerified,
    })
    .from(sessions)
    .innerJoin(users, eq(sessions.userId, users.id))
    .where(eq(sessions.id, id))
    .get();

  if (!row || row.expiresAt.getTime() < Date.now()) return null;
  return row;
}

/** Nur vollständig angemeldete Benutzer (inkl. zweitem Faktor). */
export async function getSessionUser() {
  const session = await getSession();
  return session?.mfaVerified ? session.user : null;
}

/** Nach erfolgreicher TOTP-Prüfung: Session als vollständig markieren. */
export async function markMfaVerified(): Promise<void> {
  const id = await currentTokenHash();
  if (id) await db.update(sessions).set({ mfaVerified: true }).where(eq(sessions.id, id));
}

/** Beendet die Session am Server und im Browser. */
export async function deleteSession(): Promise<void> {
  const id = await currentTokenHash();
  if (id) await db.delete(sessions).where(eq(sessions.id, id));
  (await cookies()).delete(SESSION_COOKIE);
}

9 — Umsetzung: Passkey registrieren

Für WebAuthn verwenden wir SimpleWebAuthn: ein Paket für den Server (Challenge erzeugen, Antwort prüfen) und eines für den Browser (Authenticator ansprechen). Die Registrierung braucht zwei Anfragen – genau die Schritte aus Abschnitt 5.

src/lib/webauthn.ts TypeScript 
// Relying Party: unsere Anwendung. rpID ist die Domain ohne Schema und Port.
export const RP_NAME = 'FlugBoard';
export const RP_ID = new URL(process.env.APP_URL ?? 'http://localhost:3000').hostname;
export const ORIGIN = new URL(process.env.APP_URL ?? 'http://localhost:3000').origin;
export const CHALLENGE_COOKIE = 'webauthn_challenge';
src/app/api/passkeys/register/options/route.ts TypeScript 
import { generateRegistrationOptions } from '@simplewebauthn/server';
import { eq } from 'drizzle-orm';
import { cookies } from 'next/headers';
import { NextResponse } from 'next/server';

import { db } from '@/db';
import { passkeys } from '@/db/schema';
import { getCurrentUser } from '@/lib/auth';
import { CHALLENGE_COOKIE, RP_ID, RP_NAME } from '@/lib/webauthn';

// POST /api/passkeys/register/options – Schritt 1: Challenge erzeugen
export async function POST() {
  const user = await getCurrentUser();
  if (!user) return NextResponse.json({ error: 'Nicht angemeldet' }, { status: 401 });

  const existing = db.select({ id: passkeys.id }).from(passkeys)
    .where(eq(passkeys.userId, user.id)).all();

  const options = await generateRegistrationOptions({
    rpName: RP_NAME,
    rpID: RP_ID,
    userName: user.email,
    attestationType: 'none',
    excludeCredentials: existing, // denselben Authenticator nicht doppelt registrieren
    authenticatorSelection: { residentKey: 'required', userVerification: 'preferred' },
  });

  // Challenge merken, um die Antwort später zu prüfen
  (await cookies()).set(CHALLENGE_COOKIE, options.challenge, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',
    path: '/api/passkeys',
    maxAge: 5 * 60,
  });
  return NextResponse.json(options);
}
src/app/api/passkeys/register/verify/route.ts TypeScript 
import { verifyRegistrationResponse } from '@simplewebauthn/server';
import { cookies } from 'next/headers';
import { NextResponse } from 'next/server';

import { db } from '@/db';
import { passkeys } from '@/db/schema';
import { getCurrentUser } from '@/lib/auth';
import { CHALLENGE_COOKIE, ORIGIN, RP_ID } from '@/lib/webauthn';

// POST /api/passkeys/register/verify – Schritt 2: Antwort des Authenticators prüfen
export async function POST(request: Request) {
  const user = await getCurrentUser();
  const cookieStore = await cookies();
  const expectedChallenge = cookieStore.get(CHALLENGE_COOKIE)?.value;
  cookieStore.delete(CHALLENGE_COOKIE); // jede Challenge nur einmal
  if (!user || !expectedChallenge) {
    return NextResponse.json({ error: 'Ungültige Anfrage' }, { status: 400 });
  }

  try {
    const { verified, registrationInfo } = await verifyRegistrationResponse({
      response: await request.json(),
      expectedChallenge,
      expectedOrigin: ORIGIN, // Bindung an unsere Domain
      expectedRPID: RP_ID,
    });
    if (!verified) throw new Error('nicht verifiziert');

    const { credential } = registrationInfo;
    await db.insert(passkeys).values({
      id: credential.id,
      userId: user.id,
      publicKey: Buffer.from(credential.publicKey), // nur der öffentliche Schlüssel
      counter: credential.counter,
    });
    return NextResponse.json({ ok: true });
  } catch {
    return NextResponse.json({ error: 'Registrierung fehlgeschlagen' }, { status: 400 });
  }
}
src/components/AddPasskeyButton.tsx TypeScript

Anmelden mit Passkey

Der Login funktioniert spiegelbildlich: generateAuthenticationOptions erzeugt eine Challenge, im Browser ruft startAuthentication den Authenticator auf, und verifyAuthenticationResponse prüft die Signatur mit dem gespeicherten öffentlichen Schlüssel. Danach folgt wie immer createSession.

⚠
Lokal testen

WebAuthn funktioniert nur in einem sicheren Kontext: über HTTPS oder auf localhost. Über die IP-Adresse des Rechners im Schulnetz klappt es nicht.

Häufige Fehler

3 Fehler · zum Aufklappen klicken
Fehler: Unsichere Hintertür beim Recovery

Die Anwendung verlangt Passkeys, erlaubt aber bei „Zugang verloren“ eine Wiederherstellung per SMS-Code. Angreifer nehmen einfach diesen Weg.

Recovery mindestens so stark absichern wie die Anmeldung: Recovery Codes, zweiter registrierter Faktor, Wartezeit mit Benachrichtigung.

Fehler: TOTP ohne Begrenzung der Versuche

Der Server prüft TOTP-Codes, begrenzt aber die Fehlversuche nicht. Ein Skript probiert alle sechsstelligen Codes durch.

Fehlversuche begrenzen, verwendete Codes sperren, nur ein kleines Zeitfenster zulassen.

Fehler: Zwei Faktoren derselben Kategorie

Als „2FA“ wird nach dem Passwort zusätzlich eine Sicherheitsfrage gestellt. Beides ist Wissen und kann z. B. über dieselbe Phishing-Seite abgegriffen werden.

Faktoren aus verschiedenen Kategorien kombinieren, idealerweise einen Passkey oder Security Key.

Aufgaben

3 Aufgaben + Bonus · zum Aufklappen klicken
Aufgabe 1 Faktoren bestimmen

Bestimme für jedes Verfahren die Faktor-Kategorien und entscheide, ob es sich um MFA handelt: (a) Bankomatkarte + PIN, (b) Passwort + Geburtsdatum, (c) Passkey mit Fingerabdruck, (d) Passwort + SMS-Code, (e) Schlüssel + Zahlenschloss an derselben Tür.

Aufgabe 2 TOTP einbauen

Baue die TOTP-Einrichtung und den zweiten Login-Schritt in dein FlugBoard ein. Erzeuge den ENCRYPTION_KEY mit openssl rand -hex 32. Teste mit einer Authenticator-App und prüfe in der Datenbank, dass totp_secret verschlüsselt ist.

Aufgabe 3 Recovery Codes

Erzeuge beim Aktivieren von TOTP zehn Recovery Codes (z. B. je 10 zufällige Zeichen mit randomBytes), zeige sie einmal an und speichere nur ihre Hashes in einer neuen Tabelle. Auf /login/mfa soll statt des TOTP-Codes auch ein Recovery Code akzeptiert werden – jeder genau einmal.

Bonus Login mit Passkey

Setze die Anmeldung mit Passkey um (siehe Callout in Abschnitt 9): zwei Route Handler unter /api/passkeys/login/… und einen Button auf der Login-Seite. Aktualisiere nach jeder Anmeldung den gespeicherten counter. Teste vorher die Abläufe auf webauthn.io.

Quiz

6 Fragen · zum Aufklappen klicken

Frage 1 Welche Kombination ist eine echte Multi-Factor Authentication?

Erklärung: MFA verlangt Faktoren aus verschiedenen Kategorien. Passwort (Wissen) und Authenticator-App auf dem Handy (Besitz) erfüllen das. Sicherheitsfrage und zweites Passwort sind ebenfalls Wissen, der Benutzername ist gar kein Geheimnis.

Frage 2 Wie erzeugen Authenticator-App und Server bei TOTP denselben Code?

Erklärung: Bei der Einrichtung wird per QR-Code ein Shared Secret übertragen. Danach rechnen App und Server unabhängig mit demselben Geheimnis und demselben 30-Sekunden-Zeitschritt – die App braucht dafür keine Verbindung.

Frage 3 Warum gelten Passkeys als phishing-resistent, TOTP-Codes aber nicht?

Erklärung: Einen TOTP-Code kann ein Mensch auf jeder beliebigen Seite eintippen, und eine Phishing-Seite reicht ihn in Echtzeit weiter. Bei WebAuthn übergibt der Browser die tatsächliche Domain; der Authenticator signiert nur für die Domain, für die der Schlüssel erstellt wurde.

Frage 4 Was speichert der Server bei WebAuthn/Passkeys für einen Benutzer?

Erklärung: Der private Schlüssel verlässt den Authenticator nie, biometrische Daten bleiben auf dem Gerät. Der Server kennt nur den öffentlichen Schlüssel – ein Datenbank-Leck ist dadurch für die Anmeldung wertlos.

Frage 5 Ein Angreifer schickt einem Opfer nachts dutzende Push-Anfragen, bis es auf „Bestätigen“ tippt. Welche Gegenmaßnahmen helfen?

Mehrere Antworten sind richtig.

Erklärung: Beim Number Matching muss das Opfer eine Zahl eingeben, die nur auf der Login-Seite steht – ohne eigene Anmeldung kennt es sie nicht. Passkeys erfordern gar keine Bestätigung fremder Anfragen. Das Passwort hat der Angreifer in diesem Szenario schon; SMS ist eher noch schwächer.

Frage 6 Warum wird das TOTP-Geheimnis verschlüsselt und nicht wie ein Passwort gehasht gespeichert?

Erklärung: Ein Passwort muss der Server nur vergleichen – dafür reicht ein Hash. Ein TOTP-Code wird dagegen aus dem Geheimnis berechnet, also muss der Server es wiederherstellen können. Darum Verschlüsselung, mit einem Schlüssel außerhalb der Datenbank.
